# بوابة روضة الخل وابتدائية الكواكب بالعارضة — الإصدار 10 على Supabase

هذا هو الموقع الأصلي من حزمة التسليم (`kawakib-hosting-handover`) بنفس التصميم والأقسام والأدوات.
الذي تغيّر فقط هو ما لا يعمل خارج ChatGPT:

| في النسخة الأصلية | هنا |
|---|---|
| دخول بحساب ChatGPT | دخول باسم مستخدم وكلمة مرور (Supabase Auth) |
| قاعدة D1 (Cloudflare) | Supabase Postgres بنفس الجداول: `records` `files` `organization` `members` `criteria` |
| تخزين R2 | Supabase Storage (حاوية خاصة `school-files`) |
| مسارات الخادم `app/api/*` | `src/lib/backend.ts` بنفس العناوين والرسائل والتحقق، والصلاحيات مطبّقة داخل قاعدة البيانات |
| Next.js / vinext | Vite + React (موقع ثابت يُنشر على Netlify) |

المعايير الـ54 من نسخة قاعدة البيانات الأصلية مضمّنة في `supabase/schema-v2.sql`.

---

## 1) تحديث قاعدة البيانات (مرة واحدة)
1. Supabase ← **SQL Editor** ← New snippet.
2. الصق محتوى `supabase/schema-v2.sql` كاملًا ← **Run** (إن ظهر تحذير اختر Run this query).
3. آخر نتيجة يجب أن تكون `criteria_count = 54`.

هذا الملف يحذف جداول النسخة التجريبية السابقة (كانت فارغة)، وينقل حساب المدير الحالي إلى جدول الصلاحيات تلقائيًا.

تأكد من حساب الإدارة:
```sql
select email, name, role, active from public.members;
```
إن كانت النتيجة فارغة، أضف حسابك يدويًا (بنفس الإيميل الظاهر في Authentication ← Users):
```sql
insert into public.members (email, name, role) values ('nahlaa1448@kawakib.com', 'الاسم', 'admin');
```

## 2) الدخول
- اسم المستخدم: الجزء قبل `@kawakib.com` (مثال: `nahlaa1448`) أو الإيميل كاملًا.
- الصلاحيات من «لوحة التحكم ← الحسابات والصلاحيات» كما في الأصل: إدارة كاملة، أو مسؤولة أقسام محددة.

## 3) إضافة الحسابات
- **الطريقة السهلة:** أنشئ المستخدم من Supabase ← Authentication ← Users ← Add user
  (`اسم_المستخدم@kawakib.com` + كلمة مرور + Auto Confirm)، ثم أضفه من لوحة التحكم بنفس اسم المستخدم وحدد أقسامه.
- **من داخل اللوحة مباشرة (اختياري):** انشر خدمة `admin-users` مرة واحدة، فيصبح حقل «كلمة المرور» في نموذج الحسابات ينشئ الحساب أو يغيّر كلمة مروره:
  ```
  npx supabase login
  npx supabase link --project-ref eierwruyxdteystoxgtz
  npx supabase functions deploy admin-users
  ```

## 4) النشر على Netlify (عبر GitHub)
1. في مستودع GitHub: احذف الملفات القديمة داخل مجلد `kawakib-portal`، ثم ارفع **محتويات** هذا المجلد
   **عدا** `node_modules` و `dist`.
2. في Netlify ← Site configuration ← Build & deploy ← Build settings:
   - Base directory: `kawakib-portal`
   - Build command: `npm run build`
   - Publish directory: `kawakib-portal/dist`
3. أي تعديل يُحفظ في GitHub يُبنى ويُنشر تلقائيًا.

## 5) التشغيل محليًا (للمطوّر)
```
npm install
npm run dev
```

## الحماية المطبّقة
- سياسات RLS على كل جدول تطابق قواعد الأصل (`lib/access.ts`): الزائر يرى المعتمد المتاح للنشر فقط،
  ومسؤولة القسم تعدّل أقسامها فقط، والاعتماد والنشر للإدارة فقط (مشغّل في قاعدة البيانات لا يمكن تجاوزه).
- ملاحظات المراجعة لا تصل للزائر إطلاقًا (تُحجب داخل قاعدة البيانات).
- رفع مرفق من غير الإدارة يعيد العمل إلى «بانتظار الاعتماد» ويلغي إتاحته للزائر (كما في الأصل).
- المرفقات في حاوية خاصة: PDF وصور وOffice فقط، حتى 10 ميجابايت، وتُنزّل برابط موقّع صالح دقيقتين.
- لا يمكن للمدير سحب صلاحيته عن نفسه أو إيقاف حسابه.
- سجل نشاط تلقائي (`activity_log`) لكل إضافة وتعديل، للإدارة فقط.
- قفل الدخول 15 دقيقة بعد 5 محاولات خاطئة، وخروج تلقائي بعد 30 دقيقة بلا نشاط، والجلسة تنتهي بإغلاق المتصفح.
- رؤوس أمان على Netlify (CSP، منع التضمين، HSTS…) في `netlify.toml`.

## ملاحظة عن البيانات
أسماء القيادة والفريق والقيم الافتراضية مأخوذة كما هي من مصدر الموقع الأصلي (`src/lib/staff.ts` و `src/lib/school.ts`).
بيانات المدرسة والقيادة قابلة للتعديل من «إعدادات المدرسة»، أما قائمة الفريق فتُعدّل من `src/lib/staff.ts`.
